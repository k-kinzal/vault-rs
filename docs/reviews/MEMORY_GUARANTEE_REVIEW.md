# Memory and native-key conditional-guarantee review

Baseline: `5f7400cf2f107519099c1d62aedf321beb304979`. Read-only product-source review; no hardware execution, new proof run, attack tooling, or product edits. This report proposes obligations for the new goal. Baseline release evidence does not already establish these stronger properties.

## Concrete gaps against the new request

**M1 — Production permits plaintext resident long-term scalars.** `resident.rs:26-29,68-88` stores a decrypted `p256::SecretKey` for the object's lifetime; signing also constructs a SigningKey at100. `RuntimeKeyConfig` accepts untagged Native and Resident variants and unrestricted `open` at154-182. `main.rs:500-503` and `broker.rs:304-305,392` use it without a production-native restriction. Administrative initialization/rotation use it at `main.rs:153-155,358-362`; GenerateServiceKey at213-230 creates these software keys. This was documented in the old threat model, but fails the new native-only goal.

Remove Resident from shipped runtime types/module/CLI, or make it unrepresentable in production and place any necessary legacy migration in separate explicit offline tooling. Reject old resident configurations; do not silently convert or fall back. Enforce before helper invocation, DB unwrap, network listening, or plaintext acquisition. All service, witness, broker, approval, initialization, and rotation paths must use the same protected-key contract. Test the actual unsupported config at each entry path with an adapter that detects any invocation. Keep software helper fixtures confined to verification evidence, never describe them as enrolled hardware.

**M2 — Native-only private keys do not mean no plaintext cryptographic material.** Enumerate the assets before asserting a theorem:

| Asset | Baseline behavior | Required meaning |
|---|---|---|
| Enrolled owner/device/guardian/witness/operator/storage-wrapping private keys | Native handles or exportable resident scalars | Reject resident scalars; private operations remain in enrolled protected provider |
| TLS identity private key | `main.rs:489-491` loads a PEM key into Rustls | If all long-term asymmetric private keys are included, implement native TLS signing or a separately specified protected TLS endpoint; removal of Resident alone does not cover it |
| SQLCipher generation DEK and decrypted pages | `storage.rs:247,269-276` unwraps DEK and passes it to SQLCipher | Necessarily plaintext inside the selected trusted/confidential memory boundary; not made nonresident by a native KEK |
| ECDH shared secret, HPKE keys, record shares and returned plaintext | Native ECDH and client reconstruction return derived bytes | Short-lived sensitive memory; explicitly included in the chosen boundary, not claimed absent |
| Broker DPoP and recipient private keys | `broker.rs:37-50`, `client.rs:6-8,54-56` generate per-run software keys | Ephemeral keys, not enrolled long-term keys; separate-UID protection and token+DPoP theft model still apply |
| Provider administrative credential and generated SQL password | `main.rs:580-585`, `extension.rs:103-105,150-177` expose plaintext to issuer/driver | Trusted issuer-memory boundary; native storage wrapping cannot hide values from the issuer that uses them |

A literal claim that every long-lived key is absent from RAM is incompatible with the current SQLCipher design: its generation DEK is persistent key material and must be used by the page cipher. This must be addressed by the explicit memory-boundary guarantee, not hidden by calling the DEK ephemeral. If the request covers all long-term asymmetric keys, TLS must also be fixed rather than silently excluded.

**M3 — NativeConfig is not proof of a native device.** `native.rs:52-93` checks key ID, path, owner/modes and helper digest; that correctly pins trusted code, but permits any accepted helper with the same interface. NativeKey itself retains only public configuration. Its `sign`/`ecdh` interface does not export a private scalar; actual non-exportability depends on an honest enrolled provider/helper and its OS controls. The macOS helper requests/checks Secure Enclave attributes (`SecureEnclaveHelper.swift:31-51`); Linux checks device path and returned attributes (`tpm-helper.py:42-53,82-87`). A host-controlled vTPM may satisfy those Linux checks while its state is accessible to the host. Do not combine 'host-adversary confidential VM' with an unexamined host-owned vTPM and infer non-exportability. Use an independently protected provider, attestation-bound key service, or a provider wholly inside the protected guest with an explicitly appropriate claim.

**M4 — No confidential-memory deployment verifier exists in baseline.** `readiness.rs:395-431` observes machine-id/IOPlatformUUID, executable, config and clock; those values do not establish confidential execution or prevent a hypervisor from inspecting guest RAM. Signed logs and a boolean saying confidential cannot replace verified attestation. `check_configuration:445-470` validates generic JSON/pins and acceptance signatures without typed semantic preflight of runtime key/backend/memory profile. Share a typed preflight with actual startup so readiness cannot accept a forbidden profile and merely leave later startup to reject it. Bind a profile/schema revision into signed deployment acceptance and reject missing/unknown/old profiles; old acceptance evidence cannot authorize the stronger claim by omission.

## Proposed precise theorem statements

These are separate claims with different proof status; do not label their conjunction an unconditional, machine-proved whole-system theorem.

**T1: native long-term private-key confinement.** Let K be the explicit inventory of enrolled long-term private-key roles. For every accepted production execution of the measured program, each role in K is represented only by its public identity and a handle/configuration for its enrolled protected provider. No production transition generates, deserializes, unwraps into application memory, or exports a private scalar for those roles. Assuming the provider/helper obeys its non-export and operation contract, an adversary observing application storage and permitted helper traffic does not obtain those private scalars. This is a structural/runtime-selection property plus an OS/cryptographic provider assumption, not a theorem that native hardware was exercised. It does not imply that invoking the provider is harmless: its callers must still be authorized and independent approvals must still hold.

State K explicitly. At minimum it includes all replaced Resident roles; include TLS identity if the intended promise is all long-term asymmetric runtime keys. DB DEKs, service passwords and derived secrets require T2 rather than the false assertion that they are never plaintext.

**T2a: macOS standalone DB-memory confinement.** Given trusted macOS kernel/root, protected dedicated key-owner and broker identities, correct process/ACL/FD controls, trusted service/native helper/libraries, and the specified swap/hibernation/crash/locked-device protections, arbitrary code under the separate AI/workload identity cannot directly read the unlocked DB DEK, SQLCipher plaintext pages or service credentials through memory/FD/config paths. On-disk DB/WAL/envelope confidentiality separately follows from cryptographic assumptions. This explicitly does not protect an unlocked Mac's plaintext from its compromised kernel/root, invasive physical memory acquisition, or a compromised trusted service/library. A native Secure Enclave key does not encrypt all of the app's RAM.

**T2b: confidential Linux guest DB-memory confinement.** Given a genuine supported confidential-VM implementation with the required confidentiality/integrity and debugging/migration policy, a trusted measured guest kernel/service/libraries, correct fresh remote attestation, and provisioning cryptographically bound to that guest's channel/key, a malicious host/hypervisor outside the confidential boundary cannot read the guest's private DEK/pages/issuer credentials through ordinary host memory inspection or snapshots. The AI/tool workload must remain outside that trusted guest memory domain. The guest's own root, approved service, issuer/backend and relevant firmware/CPU remain trusted. Shared I/O buffers, authorized output and declared metadata are excluded explicitly; disk/swap/snapshots must remain encrypted outside private memory. This does not assert availability or universal side-channel/physical fault resistance.

An independent ordinary VM offers process/administration separation but not this malicious-host theorem. A cloud VM with a host-owned vTPM requires separate key-protection analysis. Neither the existing native Mac tests nor Kani proves T2b; deployment needs the real supported platform's verified evidence. The physical-key experiment exclusion must not be silently repurposed as an exemption from checking the selected memory boundary.

**T3: unauthorized disclosure through the supported interface.** For every gate release of a guardian share, the exact operation must pass owner-grant, OAuth, DPoP, device/guardian signatures, record/tenant/recipient/artifact binding, current challenge/nonce, state epoch/sequence/time/remaining-use checks, and successful independent witness reservation followed by durable DB commit. A fresh recipient reconstructs/receives plaintext only through the matching broker execution. With honest independent approvers/providers and the cryptographic/OS/DB contracts, possession of the OAuth token and DPoP private key plus arbitrary AI-account code is insufficient for an additional unauthorized static-secret disclosure. Copies of legitimately delivered secrets are excluded as requested. Dynamic issuance additionally trusts the constrained issuer/provider and idempotent durable SQL behavior. Revocation cannot recall a previously committed or delivered result.

The direct Rust policy theorem proves the exact state transition and disclosure controller; the overall interface/confidentiality statement is a conditional composition argument. The existing finite TLA model is not an unbounded whole-service refinement proof, nor a liveness proof. Malicious tool dependencies are inside the adversary; malicious approved service/compiler/native-helper dependencies are a TCB violation. Reproducible builds and hashes cannot prove that all approved code is benign.

## Concrete Kani and implementation obligations

1. **Use actual production enums and fields.** Put a small `KeyBackend`/`MemoryProfile` and role policy in the shared policy/wire layer if a runtime selector remains. For example, `protected_key_allowed(role, backend)` must reject Resident/Software for every protected long-term role and accept supported Native/PKCS11 roles only. If Resident is completely removed from the runtime type, the strongest evidence is type reachability/compile and config rejection, not a meaningless Kani assertion about a constant native flag. PKCS11 support is a separate trusted protected-key adapter, not a resident fallback.
2. **Cover the complete role inventory.** A `component_keys_allowed(component, actual_role_set)` predicate should check required roles, duplicates and optional-provider roles using the real typed config. The production preflight must call it for service, witness, broker and administration. Kani can prove accepted implies every required role is protected and that valid supported inventories are accepted. Role omission and blanket denial must produce counterexamples/negative controls.
3. **Direct profile predicate.** A shared `memory_profile_allowed(profile, observed_platform, verified_binding)` should enforce MacStandalone only on Mac with explicit trusted-OS semantics and ConfidentialLinux only with the complete verified quote/channel/provisioning binding. Missing/unsupported/expired/mismatched/debug-enabled evidence must reject. Prove an iff specification on all scalar/enum inputs, plus every single-required-condition mutation; do not only prove one implication on a helper never called by startup.
4. **Actual field correspondence.** Use shared typed expected/observed attestation-binding fields, analogous to current Grant/Operation wire types. Compare fresh challenge, measured launch/config/key-generation identity, approved TCB/security policy, recipient ephemeral public key or TLS channel binding, and validity interval. Kani can prove the exact comparison and arithmetic including overflow; vendor quote signature/endorsement validation and the meaning of hardware measurements remain primitive contracts. Vendor TCB ordering is not automatically a single numeric comparison.
5. **No forged evidence constructors.** A `VerifiedMemoryBoundary` value should have private fields/no Deserialize and be produced only after a real attestation verifier plus deployment-policy check. The actual secret provisioning channel must be authenticated to the key named in the report; possession of someone else's valid quote is insufficient. A raw config `verified=true`, a machine-id or a signed generic statement must not construct this capability. In Mac trusted-OS mode the representation must explicitly encode that different trust assumption instead of pretending to hold a quote.
6. **Bind and enforce throughout the lifecycle.** Bind mode, source/build, helper/provider/key generations, database envelope and guest measurement into the accepted immutable configuration; resolve the exact same bytes at startup. Reject legacy/missing mode and mismatched platform before touching keys. Approval must authorize the selected profile, not permit an attacker to downgrade ConfidentialLinux to TrustedHost. Tie any remote key release to the accepted guest and expiration/renewal; stop/reapprove across configuration updates. Persisted witness state must remain independent of an attacker-controlled snapshot domain.
7. **Preserve existing direct proofs.** `policy::consume`, `authorize_and_commit` and `ordered_commit` already check arbitrary State/Request/Evidence and witness/commit success combinations. `protocol.rs:160-188`, `store.rs:442-454` must continue to construct the actual evidence and assign the entire next State; `store.rs:279-288` must continue to unwrap only inside the committed release closure. The broker must keep recipient/execution bindings and post-unwrap/pre-launch time checks. New backend or memory-profile code must not introduce a second unguarded release path.
8. **Do not overstate erasure.** Zeroizing Rust buffers, disabled core dumps, SQLCipher cipher_memory_security, memory locking and dump protections are useful implementation measures, but none proves absence of all compiler/library copies, registers, swap, hibernation or native helper buffers. Kani is not a proof of cryptographic secrecy, allocator erasure, kernel isolation, TPM/SE resistance, confidential-VM hardware, or the full Rust/C/compiler stack. Native/hardware and provider integration checks must be reported at their actual evidentiary level.

## Suggested acceptance wording

'For the measured release and the explicitly selected deployment profile, the actual Rust authorization and profile decisions satisfy the listed machine-checked properties. Enrolled long-term private-key roles are restricted to the specified protected providers; the program has no production Resident-key expansion path. DB keys and plaintext are confined to the declared memory trust boundary, under the named cryptographic, OS/provider, database and platform-attestation contracts. These guarantees cover the defined adversary, including token+DPoP theft and AI/tool-account compromise; they are not a claim that every real-world attack is impossible. Physical-key experiments have not been performed.'

Use this only after implementing and verifying each clause for the selected profile. The baseline cannot yet claim the Resident removal or a confidential Linux memory boundary. If MacStandalone is selected, name trusted Mac kernel/root explicitly in the displayed acceptance result; if ConfidentialLinux is selected, require real verified deployment attestation rather than substituting source review or a software quote fixture.
